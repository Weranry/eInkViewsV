# 部署与运维

本页说明 eInkViews 的三种部署形态、环境变量、反向代理与进程管理、数据备份、健康检查以及升级排查。所有端口、路径、变量名均以仓库代码为准。

## 1. 部署方式总览

项目是**双入口**，职责严格区分，不要混用：

- `run.py` — 本地完整版服务，本地测试与自托管生产共用。
- `app.py` — 专为 Vercel Serverless 的精简入口，禁止在本地启动。

| 能力 | 本地开发 `python -B run.py` | 自托管生产 `python -B run.py -prod` | Vercel `app.py` |
| :--- | :--- | :--- | :--- |
| 入口 | `run.py`（`mode='dev'`） | `run.py`（`mode='prod'`） | `app.py`（`mode='vercel'`） |
| 鉴权 | 强制关闭，注入 dev 用户 | 开启（`AUTH_ENABLE` 可关） | 开启（默认，必须配 `EVKEY`） |
| SQLite 数据库 | 启用 | 启用 | 停用（`set_db_disabled(True)`） |
| 字体 LRU 缓存 | 启用 | 启用 | 停用（`cache.set_enabled(False)`） |
| 管理面板 `/admin` | 启用 | 启用 | 不注册 |
| 请求日志 `request_logs` | 写入 | 写入 | 无日志中间件 |
| 限流 | 启用 | 启用 | 无 |
| `GET /healthz` | 注册 | 注册 | 不注册 |
| 定时预渲染 | 启用 | 启用 | 不启用（无持久存储） |
| 后台刷盘线程 | 有 | 有 | 无 |
| 首页 `/` | 走 Python 路由并改写锚点 | 同左 | `vercel.json` 指向静态文件，边缘直出 |
| 边缘缓存头 | 无 | 无 | `EDGE_CACHE_TTL` 生效 |

选型建议：

- 本机调试、内网自用：`python -B run.py`，跳过鉴权最省事。
- 有公网入口、需要账号/权限/日志/预渲染：`python -B run.py -prod` 配反向代理。
- 只需要按 key 拉图、不想维护服务器：部署到 Vercel，只用 `EVKEY` 单 key 鉴权。

## 2. 环境要求与安装

依赖只有两个文件，判据只有一句「Vercel 上用不用得到」：

| 文件 | 内容 | 谁装 |
| :--- | :--- | :--- |
| `requirements.txt` | `fastapi==0.141.1`、`httpx==0.28.1`、`Pillow==12.1.1`、`beautifulsoup4==4.14.3`、`qrcode==8.2`、`lunar-python==1.4.8` | **Vercel 构建**（`@vercel/python` 只认这个文件，装什么就都进函数包）——所以它是 Serverless 最小集 |
| `requirements-local.txt` | `-r requirements.txt` + `cachetools==7.1.4`、`uvicorn[standard]==0.40.0`、`PyJWT==2.13.0`、`redis==5.2.1` | 本地 / 单实例自托管 / 多实例（全平台自托管都装它，多出来的都是本机进程才用得到的） |

仓库**未固定 Python 版本**：没有 `runtime.txt`、`.python-version`、`pyproject.toml`。**依赖版本则全部精确锁定（`==`）**，构建结果可复现，不会被上游小版本改动悄悄改变出图或解析行为（`redis` 固定 5.x 系列：异步客户端的 pipeline 等接口在小版本之间有过不兼容改动，不跨大版本）。升级依赖时同步改两个文件，并跑一遍 `.trae/tests` 全量用例。代码使用 f-string、`asyncio`、`async def` 中间件等语法，实际按所选依赖可用的 Python 3 版本安装即可；Vercel 侧版本由 `@vercel/python` 运行时决定。

依赖文件只有这两个：**多实例不单独建文件**，与单实例装同一份 `requirements-local.txt`（旧的多实例专用依赖文件 `requirements-multi.txt` 已删除）。

```bash
pip install -r requirements-local.txt           # 本地 / 自托管（含多实例）
# Vercel 不用手装：@vercel/python 构建时自己读 requirements.txt
```

为什么 `cachetools` / `uvicorn` / `PyJWT` / `redis` 都不在 `requirements.txt`：`cachetools` 只服务字体与鉴权缓存（Vercel 侧缓存被 `set_enabled(False)` 停用、鉴权不查库，缓存从不被创建），`uvicorn` 只有自己托管 ASGI 时才用（Serverless 由平台托管），`PyJWT` 只有面板会话 Cookie 才用（Vercel 侧只有 evkey 鉴权、不发会话），`redis` 只有多实例共享状态才用。四者在 Vercel 上都用不到，放进去就是白白撑大函数包并拖慢冷启动。更要紧的是**导入链也不能碰它们**：`cachetools` 在 `auth._get_auth_cache` / `cache._ensure_cache` 函数内导入，`uvicorn` 只在 `run_core` 函数内导入，`PyJWT` 只在 `auth.create_session_token` / `decode_session_token` 内导入，redis 只在配置了 `REDIS_URL` 且要建连时才 `from redis import asyncio`（整段包在 `try` 里，失败即回落内存后端）。这条保证有回归用例：`ServerlessEntryTest` 在独立进程里跑一遍 `app.py` 的导入链，断言 `sys.modules` 里没有 redis / uvicorn / jwt / cachetools / `modules.run_core` / 本地后台线程模块。

> `httpx`、`beautifulsoup4`、`qrcode`、`lunar-python` 在启动时**不会**出现在 `sys.modules` 里（插件是请求时才 `import_module` 的），但它们在 Vercel 上会真的被用到——插件照常在 Serverless 里出图，所以必须留在最小集。别用「启动时有没有导入」当唯一判据。

两条项目硬性规则，部署时同样适用：

- **禁止创建或激活虚拟环境**（不要 `venv` / `conda` / `virtualenv`）。
- **所有 Python 命令必须带 `-B`**（如 `python -B run.py`）。原因：不生成 `__pycache__`。`run.py` 顶部会自行设置 `sys.dont_write_bytecode = True` 与 `PYTHONDONTWRITEBYTECODE=1`（`app.py` 只设前者），但命令行仍然要显式带 `-B` 保持一致。

## 3. 本地运行

```bash
python -B run.py        # 开发模式（默认）：跳过鉴权、注入 dev 用户、启用缓存与管理面板
python -B run.py -prod  # 生产模式：启用鉴权，其余同 dev
python -B run.py -h     # 打印用法
```

两种模式的区别**只在鉴权**，其余能力（缓存、SQLite、请求日志、管理面板、定时预渲染）完全一致：

- `dev`：`config.AUTH_ENABLE` 被 `config_store.enforce_mode_constraints()` 强制置为 `False`；`check_auth` 给每个请求注入 `dev` 用户（id=1，admin 组），方便直接开面板调试。
- `prod`：默认开启鉴权；环境变量 `AUTH_ENABLE=0` / `false` / `no` 可关闭。生产模式只对浏览器页面加防护头，图片响应不加。

监听地址与端口：`modules/run_core.py` 里 `uvicorn.run(app, host='0.0.0.0', port=port, log_level='warning', access_log=False)`，其中 `port = int(os.environ.get('PORT', '5000'))`，即**默认 5000**，可用环境变量 `PORT` 覆盖；host 固定 `0.0.0.0`。

启动摘要（由 `run_core.startup_banner` 与 `run_server` 打印）包含：ASCII banner、启动时间、发现的插件数/成功数/失败数、运行模式、鉴权状态、首次启动、累计运行、启动次数、累计请求、管理面板地址、启动耗时、版本、访问地址、注意事项。当鉴权已启用且未配置 `JWT_SECRET` 时，会额外打印一条告警：

```text
注意: 未设置 JWT_SECRET，管理面板会话密钥为本次进程随机值，重启后所有登录态失效
```

**为什么输出很安静**：uvicorn 以 `log_level='warning'` + `access_log=False` 启动，既不打印 uvicorn 的 INFO 启动行，也不打印逐请求访问日志。请求日志仍然正常写入数据库、并在管理面板可见，只是不刷控制台。

启动后控制台是一个交互式命令行（`help` / `routes` / `plugins` / `config` / `auth` / `cache` / `clearcache` / `stats` / `exit`）。

## 4. 环境变量总表

下表覆盖代码中真实读取的全部环境变量（`config.py` 本身不读取任何环境变量，全部配置项的默认值都写在文件里）。

| 变量名 | 默认值 | 作用 | 适用模式 |
| :--- | :--- | :--- | :--- |
| `PORT` | `5000` | uvicorn 监听端口（host 固定 `0.0.0.0`） | dev / prod（`run.py` 入口） |
| `EVKEY` | 未设置 | 鉴权密钥。请求头或查询参数 `evkey` 与之比对 | prod / vercel（dev 不校验） |
| `AUTH_ENABLE` | 未设置（等价开启） | 设为 `0` / `false` / `no` 关闭鉴权，其余值视为开启 | prod / vercel；dev 强制关闭 |
| `JWT_SECRET` | 空 | 会话 JWT 签名密钥（HS256） | dev / prod（面板登录态） |
| `JWT_EXPIRY_HOURS` | `24` | 会话有效期（小时），同时决定会话 Cookie 的 `max_age` | dev / prod |
| `PYTHONDONTWRITEBYTECODE` | 由 `run.py` 自行设为 `1` | 禁止写 `.pyc` | dev / prod |

要点：

- `AUTH_ENABLE` 的裁定逻辑集中在 `modules/config_store.py`：`dev` 模式无条件 `False`；`prod`/`vercel` 若显式设置了该环境变量则以它为准，未设置时由 `app_core` 初始化为「默认开启」。这个裁定不只在启动时做一次，面板保存/重置配置后也会重新套用。
- `JWT_SECRET` 未配置时，`modules/auth/auth.py` 退化用 `secrets.token_hex(32)` 生成进程内随机密钥：服务能跑，但进程一重启全部登录态失效，多实例部署还会互相不认（启动摘要会告警）。生产请显式设置。
- `EVKEY` 在 `prod` 下的作用范围：当数据库里没有任何账号时，鉴权回退到与 `EVKEY` 比对；数据库有账号时优先按数据库中的 evkey 匹配。`vercel` 模式不查库，直接用 `EVKEY`。
- 鉴权结果的缓存 `AUTH_CACHE_TTL`（默认 60 秒）与 `AUTH_CACHE_MAXSIZE`（默认 1000 条，面板可改）：**容量要按活跃 evkey 数取**，条目数小于在线设备数时缓存会持续抖动，每次请求都退化成查库（查库要过全局数据库锁），是这个缓存唯一要防的情况。改配置后缓存自动重建。
- Vercel 侧至少要配 `EVKEY`；未配置时所有需鉴权请求返回 401（fail-closed）。

配置项（如 `RATE_LIMIT_PER_MINUTE`、`MAX_CONCURRENT_RENDERS`、`CACHE_MAXSIZE`、`EDGE_CACHE_TTL` 等）不是环境变量，它们在 `config.py` 里给默认值，可在管理面板「配置」及相关标签页在线修改并热生效。

## 5. 自托管生产部署

### 5.1 反向代理

反向代理必须把 `X-Forwarded-Proto` 透传给后端。会话 Cookie 的 `Secure` 位由 `modules/auth/auth.py` 的 `is_https_request(request)` 判定：先读 `X-Forwarded-Proto`，没有才退回 `request.url.scheme`。**不能**用「是不是 prod 模式」来决定，否则以下是常见故障：自托管 prod 常以 `http://ip:5000` 直连，一旦给 Cookie 带上 `Secure`，浏览器根本不会回传，表现为登录成功但立刻又变未登录。

Nginx（TLS 终止）：现成示例在仓库 `deploy/nginx.conf`，拷到 `/etc/nginx/conf.d/` 后按需改域名与证书路径即可。除了指向回环的 `proxy_pass http://127.0.0.1:5000`，下面这两个头必须透传：

```nginx
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

若在代理层做 HTTP 到 HTTPS 跳转，跳转也放在 Nginx（示例里是 `listen 80` 那个 server 直接 `return 301`）；后端继续监听 `127.0.0.1`/`0.0.0.0:5000` 的明文 HTTP 即可。

Caddy（自动签发证书，自动带上 `X-Forwarded-Proto`）：示例在仓库 `deploy/Caddyfile`。

```text
views.example.com {
    reverse_proxy 127.0.0.1:5000
}
```

**挂在反向代理后面必须打开 `TRUST_PROXY_HEADERS`**（管理面板「用户 → 鉴权配置」，或直接改 `config.py`）。默认关闭时后端只认直连地址，也就是代理自己的 IP，后果有两个：所有设备共用同一份限流额度（一个人刷满、全体被限），而且同一 IP 连续登录失败会触发防撞库锁定——攻击者刷满 5 次即可把管理员一起锁在门外。

打开后来源 IP 取 `X-Forwarded-For` 的**最右一跳**（`modules/utils/client_ip.py`）：Nginx 的 `$proxy_add_x_forwarded_for` 与 Caddy 默认都是把真实来源**追加在末尾**，客户端伪造的值只留在左边，因此取最右才是本机代理写入的那一段（取最左是经典错误，等于完全放弃校验）。前提是代理确实会写入该头、且服务只监听回环或代理网段。

```text
# 管理面板 →「用户 → 鉴权配置 → 信任代理来源 IP」打开（写入 config_overrides，热生效，无需重启）
# 或直接改 config.py 的 TRUST_PROXY_HEADERS = True
```

它**不是环境变量**，只走面板配置或 `config.py` 默认值两条路径。

多级代理串联时最右一跳是上一级代理地址，这种拓扑需要按可信跳数另做处理，不在当前实现范围内。

后端在本地模式（`dev`/`prod`）还会给 HTML 页面加防护头：`X-Frame-Options` / `X-Content-Type-Options` / `Referrer-Policy`，并对 `/admin` 页面下发 CSP；请求确实走 HTTPS 时另加 `Strict-Transport-Security`（明文 `http://ip:5000` 直连不会下发，否则浏览器会把该主机永久锁在 HTTPS 里）。

### 5.2 systemd 服务单元

现成单元文件在仓库 `deploy/einkviews.service`，装法（把 `/opt/einkviews` 换成实际代码目录）：

```bash
sudo cp deploy/einkviews.service /etc/systemd/system/einkviews.service
sudo install -d -m 0750 /etc/einkviews
printf 'JWT_SECRET=%s\n' "$(python3 -c 'import secrets;print(secrets.token_hex(32))')" \
  | sudo tee /etc/einkviews/env > /dev/null && sudo chmod 600 /etc/einkviews/env
sudo systemctl daemon-reload && sudo systemctl enable --now einkviews
journalctl -u einkviews -f            # 进程日志走 journald，自带轮转
```

单元文件里几条要点：`WorkingDirectory=/opt/einkviews`、`ExecStart=/usr/bin/python3 -B run.py -prod`（`-B` 与项目规则一致：不写 `__pycache__`）、`Restart=on-failure` + `RestartSec=5`、`User=einkviews` 以非 root 运行。密钥放 `EnvironmentFile=/etc/einkviews/env` 而不是 `Environment=`：后者的内容会出现在 `systemctl show` 与进程命令行里。`data/` 必须在本机磁盘，禁止 NFS/SMB。

`run.py` 本身调用 `uvicorn.run(app, ...)`，**不能也不需要**再套一层 `uvicorn --workers`。

### 5.3 默认单进程单 worker

`modules/run_core.py` 的 `uvicorn.run` 禁止加 `workers=N`（同机多 worker 一律禁止）。原因：

- **内存限流会变成 N 倍宽松**：滑动窗口计数在进程内存里，每个 worker 各记一份，配额实际被放大 N 倍。
- **字体 LRU 缓存会分裂成 N 份**：命中率下降、内存占用翻倍。
- 这两种失效都**静默发生、不报错**，从外部看只是「限流失效」「内存偏高」，很难定位。

需要横向扩展时走下面 5.5 的「多实例 + 外部共享存储」，**不要**改成同机多 worker。

### 5.4 Docker 部署要点

`deploy/Dockerfile` 与 `deploy/docker-compose.yml` 是可直接用的产物（单实例自托管；Vercel 部署不用它们）：

```bash
cd 仓库根目录
export JWT_SECRET=$(python3 -c "import secrets;print(secrets.token_hex(32))")
docker compose -f deploy/docker-compose.yml up -d --build     # 或下面的原生命令
```

```bash
docker build -f deploy/Dockerfile -t einkviews .
docker run -d --name einkviews -p 5000:5000 \
  -e JWT_SECRET=请替换为足够长的随机串 \
  -v einkviews-data:/app/data \
  einkviews
```

镜像里的几个刻意选择：基础镜像是 `python:3.12-slim`（Pillow 有 manylinux/aarch64 wheel，无需编译器）；装依赖用 `requirements-local.txt`；`ENV PYTHONDONTWRITEBYTECODE=1` 且启动命令为 `python -B run.py -prod`（与项目规则一致：不写 `__pycache__`）；`useradd` 出来的 `einkviews` 用户以非 root 运行；`HEALTHCHECK` 打 `/healthz`；`VOLUME /app/data` 承接数据库与备份。仓库根的 `.dockerignore` 排除了 `data/`——库里含密码哈希与 evkey，打进镜像层等于把凭据随镜像分发出去。

`deploy/docker-compose.yml` 是**单实例**编排：`data/` 用**具名卷**持久化（容器重建不丢库文件与历史备份），`JWT_SECRET` 走环境变量（缺失时 compose 直接报错退出，不会悄悄起一个会掉登录态的服务）；单实例**不配 `REDIS_URL`**（共享层自动回落进程内存后端）、也**不加 `workers=` 参数**（见 5.3）。

必须把 `data/` 挂出来：数据库文件（以及 `-wal` / `-shm`）都在这里，容器只读层重建就等于清库。探针请用 `/healthz`，不要用 `/`。

### 5.5 ARM 小主机部署（Orange Pi Zero 2W 等）

可以，而且相当合适：项目的每个请求都是「取数据 → 排版 → 编码 → 返回字节」，没有长驻重活，单进程占用的常驻内存很小（主要是 Pillow 与字体缓存），Zero 2W 那档硬件（全志 H618 四核 A53 + 1~4GB 内存）跑单实例绰绰有余。按第 3 节直接跑即可：

```bash
# 系统依赖：Pillow 官方只为 aarch64 提供 wheel；armhf(32 位) 上多半要就地编译
sudo apt update && sudo apt install -y python3 python3-pip libjpeg-dev zlib1g-dev
pip3 install -r requirements-local.txt      # 自托管一律装这个（含 cachetools/uvicorn/PyJWT/redis）
python3 -B run.py -prod
```

注意这几点：

- **优先用 64 位系统（aarch64）**。Pillow / uvicorn 的 `[standard]` 加速件在 aarch64 上有预编译 wheel，装得又快又不折腾；如果装的是 32 位 `armhf`，`libjpeg-dev` / `zlib1g-dev` 基本是必需的（否则 `pip install Pillow` 直接编译失败），而且没有 `uvloop`，异步性能会差一截。
- **`JWT_SECRET` 一定要显式配**（systemd 单元的 `Environment=` 或 `EnvironmentFile=`）：不配会退化成每次启动随机生成，重启一次所有登录态失效。
- **库文件放本机存储**（默认 `data/`，microSD 或 eMMC 都行）。**不要放 NFS/SMB 挂载的网络盘**，原因见 5.6 的 SQLite 硬约束。
- **单实例不要装/配 Redis**：`REDIS_URL` 默认空，此时共享层直接跑进程内存后端，行为与未启用时完全一致。若以后真要多实例，再按 5.6 配 `REDIS_URL`——在同一台 Zero 2W 上跑一个 `redis-server` 也够（它常驻只要几 MB），但那样多实例仍旧共用一个库文件，收益有限。
- **别加 `workers=N`**：见 5.3（Zero 2W 内存有限，多 worker 还会让缓存与限流各自分裂成 N 份）。
- 内存紧张时可以把 `CACHE_MAXSIZE`、`PRERENDER_MEMORY_CACHE_MB` 调小或设为 `0`，详见第 9 节。

### 5.6 多实例部署（可选，需要 Redis）

默认部署是单进程单 worker。要让**多个实例**同时对外服务，把跨实例状态挪到外部共享存储即可——先给每个实例装上多出来的那个依赖，再在管理面板「配置 → 共享存储」里填 `REDIS_URL`（这是**配置项**，不是环境变量；默认空 = 单实例，行为与未启用时完全一致）：

```bash
pip install -r requirements-local.txt     # 已含 redis（单实例装的也是它）
```

redis 客户端不装也能跑（会自动回落内存后端），但那样多实例之间就不共享计数了，等于白扩。

启用后：

- **跨实例共享**：每分钟/每小时的限流计数、登录防撞库的失败次数与锁定、单例租约、内存态失效版本号，全部走 Redis（`modules/shared/`），多个实例共用同一份额度。
- **不共享（各实例各算）**：渲染并发信号量、字体 LRU 缓存、预渲染内存成品缓存。这些都是本进程内的资源，多实例部署时不要假设它们全局一致；`PRERENDER_MEMORY_CACHE_MB` 设为 `0` 可以彻底去掉最后一项。
- **单例 leader**：每个实例轮询抢一个租约（`SHARED_LEADER_TTL_SECONDS`，默认 30 秒，按 1/3 续租），只有持有者执行预渲染调度、到期归位扫描与日志/审计/成品缓存裁剪；其余实例照常出图、照常把**自己**的日志与统计刷进库。`/metrics` 的 `einkviews_shared_leader` 能看出谁是 leader（全是 0 = 租约没抢到，全是 1 = 共享存储实际没生效，两种情况都该告警）。
- **失效延迟**：某实例改了账号/权限/限额后，其它实例最长 `SHARED_POLL_SECONDS`（默认 5 秒）后生效（版本号轮询，不做长连接订阅）。
- **Redis 故障时的表现**：默认（`SHARED_FALLBACK_LOCAL=True`）**自动回落进程内存计数**并置降级标志（`/metrics` 的 `einkviews_shared_backend{degraded="1"}` 与面板可见），服务照常出图——代价是降级期间各实例计数不再共享（限流会暂时宽松 N 倍），且可能出现两个 leader；恢复后自动回到共享模式并对全部内存态做一次失效。若把 `SHARED_FALLBACK_LOCAL` 设为 `False`，Redis 不可用时**连本地计数也不做、一律放行**（fail-open，降级期限流与防撞库完全失效）——只在「宁可漏放也不能误伤」时才这样选。两种设置都**不会**返回 503。

SQLite 的硬约束（多实例时必读）：

- 各实例**必须共用同一个库文件**，且该文件必须在**同一台机器**的本地可靠卷上。**禁止 NFS / SMB / CIFS 等网络文件系统**——WAL 依赖共享内存与文件锁，网络文件系统上会静默损坏。
- SQLite 是**单写者**模型：一个库文件同一时刻只有一个写事务。代码已开 `PRAGMA busy_timeout=5000`，并发写会等锁而不是立刻报 `database is locked`；写密集路径（请求日志、统计）已用队列 + 批量事务 + 分批 DELETE 收窄，但**这不等于可以随便加实例**——控制在个位数，要真正的并行写就得换 Postgres 一类外部数据库（不在本项目范围）。
- 多实例必须配**同一个** `JWT_SECRET`，否则各实例签发的管理面板会话互相不认（启动摘要会告警）；`SHARED_KEY_PREFIX` 也要一致，多套部署共用一个 Redis 实例时靠它隔离。

## 6. Vercel 部署

步骤：

1. 把仓库导入 Vercel，构建与路由交给 `vercel.json`（`@vercel/python` 构建 `app.py`，`@vercel/static` 处理 `public/**`）。
2. 在项目设置里配置环境变量：`EVKEY`（必填）、按需 `AUTH_ENABLE`。
3. 部署后访问站点根路径确认首页正常，再用带 `evkey` 的请求调用图片路由。

**依赖只装 `requirements.txt`**：`@vercel/python` 固定读 `requirements.txt`，不读 `requirements-local.txt`，所以函数包里既没有 `uvicorn` / `PyJWT`、也没有多实例可选用的 `redis`、更没有 `cachetools`——这正是把依赖分两个文件的原因（见第 2 节）。运行时也不会导入它们：`cachetools` 在 `auth._get_auth_cache` / `cache._ensure_cache` 函数内导入，`uvicorn` 只在 `run_core` 函数内导入，`PyJWT` 只在 `auth.create_session_token` / `decode_session_token` 内导入，`from redis import asyncio` 只在「配了 URL 且要建连」时才执行（`REDIS_URL` 是配置项、默认空）。`tests/test_app_smoke.py` 的 `ServerlessEntryTest` 会在独立进程里跑一遍 `app.py` 的导入链并断言拿不到 redis / uvicorn / jwt / cachetools / `modules.run_core` / 本地后台线程模块，可本地执行复核（测试目录在 `.trae/tests`）：

```bash
python -B -m unittest discover -s .trae/tests -p "test_app_smoke.py"
```

**不要把 `cachetools` / `uvicorn` / `PyJWT` / `redis` 加回 `requirements.txt`**：那会让它们在 Vercel 构建期被安装进函数包（体积与冷启动白白增加），而 Serverless 侧永远用不到它们。

`vercel.json` 全文（仓库根目录，`version` / `builds` / `routes` 三段）：

```json
{
  "version": 2,
  "builds": [
    { "src": "app.py", "use": "@vercel/python" },
    { "src": "public/**", "use": "@vercel/static" }
  ],
  "routes": [
    { "src": "/favicon.ico", "dest": "/public/favicon.ico" },
    { "src": "/public/(.*)", "dest": "/public/$1" },
    { "src": "/", "dest": "/public/pages/index.html" },
    { "src": "/(.*)", "dest": "/app.py" }
  ]
}
```

关键是 `routes` 里的最后三条（按顺序匹配）：

```text
/public/(.*)  ->  /public/$1                     静态资源直出
/             ->  /public/pages/index.html       首页走边缘静态，不经过函数
/(.*)         ->  /app.py                        其余全部落到 Serverless 函数
```

也就是说 `/` **直接命中静态文件 `public/pages/index.html`，完全不经过 Python 函数**（零冷启动）；只有其余路径才落到 `app.py`。

`app.py` 的顶层入口必须写成**单个 Name 赋值**：

```text
app = create_app(mode='vercel')[0]
```

Vercel 的 `@vercel/python` 用 AST 静态分析在 `app.py` 里找 `app` / `application` / `handler`。元组解包（`app, _ = ...`）的赋值目标是 `ast.Tuple`，它识别不出来，会在构建期直接报 `Could not find a top-level "app", application, or handler in app.py`。

Vercel 模式下的降级行为：

- 数据库停用：`create_app` 调用 `set_db_disabled(True)`，之后 `_connect()` 首行即抛 `DatabaseUnavailable`，连数据库路径都不解析、`data/` 目录都不创建。
- 缓存停用：`cache.set_enabled(False)`，字体每次实时加载，LRU 池一条都不写。
- 不启动 lifecycle、后台刷盘线程、请求日志中间件、限流中间件与管理面板路由。
- 鉴权只认 `EVKEY`；未配置时所有需鉴权请求 401（fail-closed）。
- 图像响应可带 `Vercel-CDN-Cache-Control`（由 `EDGE_CACHE_TTL` 控制，仅 `vercel` 模式生效）。该头不会返回给客户端，因此不会触发设备端缓存；命中边缘缓存时函数不执行，也就没有鉴权、限流、日志与统计——这是刻意取舍。

不要往 Serverless 链路加任何端点或功能：`/healthz` 只在本地链路注册，首页走边缘静态直出，Vercel 侧没有持久存储，任何依赖数据库/缓存的功能都进不去。

首页 `public/pages/index.html` 是「Vercel 静态直出版」：随环境变化的文案/入口一律存 **Vercel 版**并用锚点包住，本地 `dev`/`prod` 下由 `modules/register/template_routes.py` 的 `_LOCAL_BLOCKS` 改写。当前有两个锚点：`env-note`（副标题）与 `admin-entry`（footer 登录入口）。不要往这个静态文件里直接写 `/admin/login` 之类的本地专属链接，否则在 Vercel 直出时会变成死链。

## 7. 数据与备份

数据统一放在项目根目录的 `data/`（目录与文件自动创建）：

```text
data/einkviews.db        # SQLite 数据库，启用 WAL 模式与 foreign_keys
data/einkviews.db-wal    # WAL 日志
data/einkviews.db-shm    # 共享内存索引
```

- **禁止把数据库放到 `public/` 下**：`public/**` 会被 `/public` 路由与 Vercel static build 直接对外提供，数据库里含密码哈希与 evkey，放进去等于公开下载。`data/` 不是静态目录，不会被 HTTP 下载。
- 从旧版本升级：若项目根目录存在 `einkviews.db`，首次启动时会自动 `os.replace` 迁移到 `data/`。不要手工复制，避免丢失数据。
- 数据库连接开启 `PRAGMA journal_mode=WAL`（读不阻塞写，日志中间件每请求都写库）、`PRAGMA foreign_keys=ON` 与 `PRAGMA busy_timeout=5000`（写锁冲突时等一会儿而不是立刻抛 `database is locked`，多实例共享库文件时必需；单实例下代价为零）。

备份与恢复建议：

- **拿得到管理面板时优先用面板「备份」页**：`下载当前备份` 走 SQLite 官方在线备份接口（一致性快照，服务写入中导出也安全），`上传并恢复` 会在替换前自动把当前库存到 `data/backups/einkviews-auto-<时间戳>.db`，随后整体换库并重建全部内存态，成功后所有登录态失效。详见[使用手册 · 备份](使用.md#备份)。
- **拿不到面板时用 SQLite 在线备份**，不要直接 `cp` 主文件：

```bash
sqlite3 data/einkviews.db ".backup 'backup/einkviews-$(date +%F).db'"
```

- 若坚持文件级复制，先停服务（或至少先确认没有写入），并且**把 `.db`、`-wal`、`-shm` 三个文件一起取**：只拷 `.db` 会丢掉还在 WAL 里、尚未 checkpoint 的最近提交。
- 手动恢复：停服务，把备份放回 `data/einkviews.db`，并**先删掉残留的 `-wal`/`-shm`**（正常关闭会自行 checkpoint 并删除；异常退出留下的旧 WAL 拼到新库上会被读成「库损坏」），再启动。
- Vercel 环境无持久存储，数据库自动降级，谈不上备份。

## 8. 健康检查与可观测性

存活探针 `GET /healthz`（**只在 dev/prod 注册**，Vercel 侧没有）返回：

```json
{
  "success": true,
  "status": "ok",
  "mode": "dev",
  "version": "26.9.1"
}
```

`mode` 与 `version` 来自应用状态与 `app.version`，便于外部监控区分部署形态。它**不查库、不渲染、不写请求日志、不占限流额度、也不需要 evkey**，因此被高频轮询也不会把 `request_logs` 刷满或吃掉限流额度。为此，`/healthz` 必须同时出现在三处：

- `config.AUTH_WHITELIST`（免鉴权）
- `config.RATE_LIMIT_WHITELIST`（不占限流额度）
- `modules/app_core.py` 的 `_LOG_SKIP_PREFIXES`（不写请求日志）

监控接法：

- Uptime Kuma：新建 HTTP(s) 监控，URL 填 `http://<host>:5000/healthz`，关键字校验可填 `"status":"ok"`。
- systemd：配合服务单元的 `Restart=on-failure`，或用定时任务 `curl -fsS http://127.0.0.1:5000/healthz`。
- Docker：见上一节的 `HEALTHCHECK` 指令。

### 8.1 Prometheus 指标 `/metrics`

`GET /metrics`（**同样只在 dev/prod 注册**）输出 Prometheus 文本格式，由 `modules/utils/metrics.py` 手写、不引第三方库。与 `/healthz` 同源：免鉴权、不占限流额度、不写请求日志（同样在 `AUTH_WHITELIST` / `RATE_LIMIT_WHITELIST` / `_LOG_SKIP_PREFIXES` 三处生效）。默认对所有人开放；在面板「配置 → 管理面板」里把 `METRICS_TOKEN` 设为非空后，必须带 `?token=<令牌>` 或 `Authorization: Bearer <令牌>`，否则 403。

抓取示例：

```yaml
scrape_configs:
  - job_name: einkviews
    static_configs:
      - targets: ['127.0.0.1:5000']
    metrics_path: /metrics
```

导出内容按子系统分组（每段独立兜底，某个子系统不可用只少几行、不会整个 500）：

| 前缀 | 关键指标 |
| :--- | :--- |
| `einkviews_info` / `einkviews_uptime_seconds` / `einkviews_process_rss_bytes` / `einkviews_db_size_bytes` | 模式与版本、运行时长、进程常驻内存、库文件大小 |
| `einkviews_render_*` | 当前渲染并发、累计渲染次数、成品缓存命中、最近/平均/最慢耗时、**并发信号量条目数** |
| `einkviews_plugin_requests_total{plugin=...}` / `einkviews_plugins_loaded` | 各插件累计请求数、已加载插件数 |
| `einkviews_rate_limit_rejected_total` / `einkviews_rate_limiter_keys` | 被限流拒绝的请求数、限流器追踪的 key 数 |
| `einkviews_auth_cache_*` | 鉴权缓存条目数 / 上限 / 命中 / 未命中——**命中率骤降就说明容量小于在线设备数**，每个请求都在退化成查库（过全局数据库锁） |
| `einkviews_shared_backend{backend,degraded}` / `einkviews_shared_leader` | 共享后端类型与是否降级、本实例是否持有租约（多实例部署用，见 5.5） |
| `einkviews_log_queue_*` / `einkviews_font_cache_*` / `einkviews_prerender_*` | 日志队列占用与丢弃、字体缓存、预渲染成品与内存缓存 |

指标全部来自**进程内已有的计数**，只有库大小与成品缓存条数需要读库（O(1) / O(小表)），按秒轮询的代价可忽略；注意它们在**重启后归零**，长期趋势请以数据库里的统计为准（多实例下每个实例各报一份，属于预期）。

### 8.2 请求追踪 `X-Request-ID`

`request_log_middleware`（`modules/app_core.py`）为每个请求生成或**复用** `X-Request-ID`（请求头已带则原样沿用），写入 `request.state.request_id` 并在响应头回写。请求出错时，`traceback.print_exc()` 之前会先打一行 `[req=<id>] METHOD PATH STATUS <ms>`，把控制台上的堆栈和具体请求对上。排查时先拿这个 id 在控制台里搜，再结合面板日志页的路径/状态码定位；上游（代理、客户端）也可以自己生成一个 id 传进来，全链路就能串起来。

管理面板概览的数据源 `GET /admin/api/status` 带有 **3 秒 TTL 的短缓存**（`cachetools.TTLCache(maxsize=1, ttl=3)`）：其中的数据库查询、`shutil.disk_usage`、`os.path.getsize`、多项健康自检等昂贵项在窗口内复用上次结果；运行时长、请求计数、今日指标变化快且零成本，放在缓存外重算。因此面板 10 秒一次的轮询不会每次都重做真开销。该接口还包含渲染维度自检（渲染并发占用、最近一次渲染耗时）与日志队列占用/丢弃条数。

`/admin/api/**` 落在鉴权白名单前缀 `/admin` 里，但白名单只代表「不校验 evkey」，不代表免授权：`app_core._check_admin_api_access()` 会额外把关——本地模式下 `/admin/api/**` 必须是已登录的**管理组**（`category = admin`）用户，且该管理组开放了对应后台分页（映射见 `modules/admin/tab_access.py`，未登记的路径放行、由测试全量覆盖兜底）；仅 `/admin/api/auth/*` 与 `/admin/api/my/*` 例外（由各自路由内校验身份）。

## 9. 运维与调优

### 字体缓存

- `CACHE_MAXSIZE`（默认 64）是字体 LRU 池的最大条目数，**不过期**。只缓存字体：字体文件运行期不变、FreeType 解析成本高，带 TTL 反而有害（ESP32 每 5~15 分钟轮询一次正好踩在过期边界）。图片不进池，`get_image()` / `get_indexed_image()` 只做实时解码。
- 池按 `CACHE_MAXSIZE` 现取重建，面板改完立即生效（`/admin/api/status` 与缓存页显示的也是新值）。2GB 生产内存下按「插件数 × 每视图字号数」估算即可。

### 并发

并发限制有两处来源，**用户组的值优先于全局，且 0 = 不限**：

- 全局 `MAX_CONCURRENT_RENDERS`（默认 4）。
- 用户组 `max_concurrent_renders`（数据库默认 5）。

内部实现对「不限」用值 1000000 的信号量表示。信号量**按账号**缓存于 `app.state.render_semaphores`（值为 `(group_id, semaphore)`）；无用户身份（如 `EVKEY` 环境变量鉴权）时用全局上限且不缓存。修改用户组的并发值后，`admin_routes` 必须丢弃该组下所有账号的信号量，否则要重启才生效。`RENDER_SLOW_MS`（默认 2000）用于健康检查里标记「偏慢」。

这份缓存是 LRU：超过 `RENDER_SEMAPHORE_MAXSIZE`（默认 2000，`0` = 不限）就从最久未访问端淘汰，防止账号被大量增删/轮换时字典只增不减。删除账号、批量转移/删除账号后会主动丢弃对应条目；淘汰到正在使用的信号量只会让该账号短暂回落到全局上限（等价于重建），是有意取舍。

### 请求日志双重上限

- 按天清理：`REQUEST_LOG_RETENTION_DAYS`（默认 7 天）。
- 按条数淘汰：`REQUEST_LOG_MAX_ROWS`（默认 10000，超出淘汰最旧；0 = 不限）。
- 写入走队列 `LOG_QUEUE_MAXSIZE`（默认 5000），队列写满会丢弃；丢弃条数在日志页与管理面板可见，不会静默。
- 清理挂在后台刷盘线程里，每 `LOG_CLEANUP_CYCLES`（默认 20）个周期执行一次；周期 = `STATS_FLUSH_INTERVAL`（默认 30 秒），即约 600 秒。审计日志另有 `AUDIT_LOG_MAX_ROWS`（默认 5000）。删除按 5000 行分批执行，避免长时间持有全局锁卡住请求。

### 日志收集与轮转

进程日志默认只写 stdout：普通信息只写消息本身，只有 `[WARN]` / `[ERROR]` 带级别前缀，整行**不带时间戳**（要时间就用 `docker logs -t`、journald 或面板里的请求日志，那些本来就是 UTC、能互相对齐）。容器部署交给 log driver、systemd 交给 journald 收集，两者自带轮转，此时**不必**再开文件轮转。

需要落文件时用面板配置（详见[参数](参数.md)）：

- `LOG_FILE`：文件路径，**留空 = 只写 stdout**（默认行为）。
- `LOG_MAX_BYTES`：单个文件的字节上限，`0` = 不按大小轮转（一直追加）。
- `LOG_BACKUP_COUNT`：轮转时保留的历史份数，`0` = 不留历史（超出即清空当前文件）。

分清两条链路：**进程日志**（启动提示、告警、异常堆栈）走 stdout / 可选文件；**请求日志**进数据库、由面板「日志」页查询与导出，不受上面三项影响。

备份目录 `data/backups/` 建议纳入备份或监控：它会自动累积（恢复前的自动快照、可选的每日自动备份都落在这里），保留策略由「保留份数 / 保留天数」控制。

### 统计刷盘

`STATS_FLUSH_INTERVAL`（默认 30 秒）是后台线程的刷盘间隔：把内存里的插件请求计数、账号维度用量、日志队列、预渲染命中计数落库，并按 `_SESSION_HEARTBEAT_SECONDS`（默认 300 秒）打一次会话心跳。心跳与刷盘周期**解耦**：空闲站点上它是唯一"每轮必写"的语句，跟着 30 秒走等于每天近三千次写库，在 SD 卡部署上是白付的磨损。进程被强杀时，下次启动按心跳时间收尾会话，不会把停机时长算进运行时长；正常退出另由 `flush_and_close` 收尾。

### 定时预渲染

仅本地 `dev`/`prod` 生效：

- `PRERENDER_ENABLE`（默认 True）总开关。
- `PRERENDER_TICK_SECONDS`（默认 10）调度循环检查间隔。
- `PRERENDER_STARTUP_GRACE_SECONDS`（默认 30）启动后延迟首轮调度，避开启动期。
- `PRERENDER_TIMEOUT_SECONDS`（默认 30）单任务渲染超时。
- `PRERENDER_MAX_CONCURRENCY`（默认 1）同时执行的预渲染任务数，默认串行以避免后台渲染抢占屏端请求的 CPU。
- 成品缓存上限 `PRERENDER_CACHE_MAX_ROWS`（默认 200 条）与 `PRERENDER_CACHE_MAX_MB`（默认 64MB），超出按「最久未被请求」淘汰；每个任务另有 `cache_ttl_hours`（`0` = 不因空闲过期）。
- 命中路径的内存成品缓存 `PRERENDER_MEMORY_CACHE_MB`（默认 32MB，`0` = 关闭）缓存**已编码好的响应体**，命中时不再读产物 BLOB、不再解码索引图、不再重新编码（实测命中路径从约 0.9ms 降到约 0.003ms）。同一份产物按「格式 + 旋转 + 反色 + cmode」各占一份；所有删除/覆盖产物的入口都会整体清空它。**多实例部署时它只作用于本实例**（各实例各自缓存、各自淘汰），若需要跨实例即时一致可设为 `0`。
- **排期**三种：固定间隔（`interval_seconds`）、每日多个 `HH:MM`（空格或逗号分隔）、5 段 cron（分 时 日 月 周；支持 `*` / `n` / `a-b` / `*/n` / `a-b/n` / 逗号列表）。非法表达式**整体判非法并报 400**，不静默少排——少排一个时刻比报错更难排查。
- **失败告警**：任务状态为「失败」或「路由失效」时，向 `PRERENDER_ALERT_WEBHOOK`（留空 = 关闭）POST 一份通用 JSON（任务名、插件、路由、状态、错误、耗时、发生时间、实例标识），方便接企业微信/钉钉/Slack 的中转。同一任务在 `PRERENDER_ALERT_MIN_INTERVAL`（默认 600 秒，`0` = 每次都发）内只发一次；发送失败只打印堆栈，不影响调度。
- 多实例部署时**只有 leader 实例**执行调度（见 5.5），其余实例仍照常命中成品缓存。

### 限流

- `RATE_LIMIT_ENABLE`（默认 True）总开关。
- 无用户组身份时回落到全局 `RATE_LIMIT_PER_MINUTE`（默认 30）/ `RATE_LIMIT_PER_HOUR`（默认 1000）。
- 有用户组身份时，组限额取代全局（组值为 0 即真的不限，不叠加全局）：`rate_limit_per_minute` 与 `quota_limit` + `quota_period`。计数**按账号**，同账号下所有 evkey 共用一份额度。
- 限流器内部存储上限 `RATE_LIMITER_STORE_MAXSIZE`（默认 10000）。命中限流返回 429，响应可带 `X-RateLimit-Limit` / `X-RateLimit-Remaining` 与 `X-RateLimit-Long-*` 头。
- 配置了 `REDIS_URL` 后计数落在 Redis（两个时间窗合成一次 Lua 往返，带 `SHARED_TIMEOUT_MS` 超时），多实例共用同一份额度；Redis 不可用时自动回落进程内存并置降级标志，被拒总数可在 `einkviews_rate_limit_rejected_total` 上观察。

## 10. 升级与故障排查

### 升级步骤

1. 备份数据库（见第 7 节）。
2. 拉取新代码并重装依赖：`pip install -r requirements-local.txt`（自托管/多实例都是这一条命令）。
3. 判断改动范围：
   - 只改 `plugins/**`（视图/JSON）：可在面板插件页点「热重载」（`POST /admin/api/plugins/reload`），不必重启进程。
   - 改了 `modules/**` 等框架代码、`config.py`、`run.py`：**必须重启进程**，热重载不覆盖框架代码。
4. 重启服务，查看启动摘要确认插件加载数、鉴权状态与版本。
5. 自检 `GET /healthz` 与管理面板概览的健康检查项。

### 常见故障

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| 启动后立即退出，只打印「致命错误: FastAPI 应用初始化失败」 | `create_app` 组装期抛异常（依赖缺失、插件脚手架语法错误等） | 先带 `-B` 手动运行看完整堆栈；确认 `pip install -r requirements-local.txt` 已执行、`plugins/**` 可导入 |
| 启动即报数据库相关错误 / `database is locked` | 单实例下：另一个进程仍占用同一个 `data/einkviews.db`（旧实例未退干净、或用了多 worker，后者本身违规）。多实例下：写锁竞争（已开 5 秒 `busy_timeout`，持续报错说明某个实例卡在长事务或库在慢速/网络文件系统上） | 单实例：结束旧进程、确认没有 `workers=N`。多实例：确认库文件在本地卷（禁止 NFS/SMB）、实例数在个位数；必要时查 `einkviews_db_size_bytes` 与日志刷盘情况 |
| 限流突然变宽松、防撞库失效、`/metrics` 出现 `einkviews_shared_backend{degraded="1"}` | 配置了 `REDIS_URL` 但 Redis 连不上/超时，已自动回落到进程内存计数（各实例各算一份，所以变宽松） | 检查 Redis 连通性与 `SHARED_TIMEOUT_MS`；这是默认的 fail-safe 行为。若把 `SHARED_FALLBACK_LOCAL` 设成了 `False`，降级期会**一律放行**（限流完全失效），排查完记得改回 `True` |
| 多实例下反复出现「一会儿是 A 在调度、一会儿是 B」或到期归位重复执行 | 共享租约没抢稳（TTL 过小 / Redis 抖动降级），降级期可能同时存在两个 leader | 确认 `SHARED_LEADER_TTL_SECONDS`（默认 30）与 Redis 稳定性；重复执行的都是可重入的调度与裁剪，不影响正确性 |
| 请求耗时整体升高，`einkviews_auth_cache_hits_total` 涨得比 `misses` 慢很多 | 在线 evkey 数超过 `AUTH_CACHE_MAXSIZE`，缓存持续抖动，每个请求都退化成查库（过全局数据库锁） | 把 `AUTH_CACHE_MAXSIZE` 调到不小于在线设备数（面板「配置 → 鉴权」）；命中率在 `/metrics` 与面板缓存页可见 |
| 设备收到的是「参数没生效」的正常图 | 请求里 `rotate` / `invert` / `cmode` / `size` 拼错了 | 现在非法值一律返回 **400** 并在消息里给出合法取值（不再静默回落），按消息改请求即可 |
| prod 下浏览器直接打开 `/docs` 是 401 / 一片空白 | FastAPI 自带的 `/docs` 落在鉴权范围内，prod 下被挡死（不是故障，是有意为之） | 用面板的「测试 → 接口清单」（`GET /admin/api/api-docs`），它列出全部路由、方法与是否需要 evkey |
| 登录成功但立刻又变未登录（面板反复跳登录页） | 反向代理没透传 `X-Forwarded-Proto`，或后端误给 Cookie 加了 `Secure`，浏览器不回传 | 在代理里加 `proxy_set_header X-Forwarded-Proto $scheme`；`Secure` 由 `is_https_request()` 自动判定，不要手工写死 |
| 重启后所有人登录态失效 | 未配置 `JWT_SECRET`，会话密钥是本次进程的随机值 | 显式设置 `JWT_SECRET`（多实例部署必须一致），重启后会看到告警文字 |
| 反代后所有设备共用一份限流额度、一个 IP 连续失败就把管理员也锁在门外 | `TRUST_PROXY_HEADERS` 仍为默认 `False`，后端只看到代理自己的 IP | 面板「用户 → 鉴权配置」打开「信任代理来源 IP」；前提是代理确实写入 `X-Forwarded-For`（取最右一跳） |
| 所有需鉴权请求 401 全部失败 | `prod`/`vercel` 下 `EVKEY` 未配置，或请求没带正确的 `evkey` | 配置 `EVKEY`，请求头或查询参数带上 `evkey`；确认没有把 `AUTH_ENABLE` 误设为 `0` 造成相反问题 |
| 图片渲染很慢 | 并发打满（信号量占尽）、未命中预渲染缓存、或字体缓存被关/容量过小 | 看面板概览的「渲染并发」「最近渲染耗时」；提高 `PRERENDER_MAX_CONCURRENCY` 或为热点路由建预渲染任务；适度调大 `CACHE_MAXSIZE` |
| `request_logs` 增长过快 | 监控轮询打到了 `/` 或图片路由而非 `/healthz`；或保留上限过大 | 把探针改成 `/healthz`；下调 `REQUEST_LOG_RETENTION_DAYS` / `REQUEST_LOG_MAX_ROWS`；注意 `/admin` 前缀本身不写请求日志 |
| Vercel 上出现 500，日志指向文件写入失败 | Serverless 只读文件系统不允许本地临时文件；有功能试图写盘/建库 | 不要在 Vercel 链路使用数据库、缓存或本地临时文件；图像处理一律走 `io.BytesIO`；确认 `app.py` 构造函数未被本地化改造 |
| Vercel 构建报 `Could not find a top-level "app"` | `app.py` 顶层入口不是单个 Name 赋值 | 恢复为 `app = create_app(mode='vercel')[0]`，不要元组解包 |
| 改了插件代码但页面没变化 | 只改了 `plugins/**` 且尚未触发热重载，或改动其实在 `modules/**` | 面板点「热重载」；若改的是 `modules/**`，重启进程 |
